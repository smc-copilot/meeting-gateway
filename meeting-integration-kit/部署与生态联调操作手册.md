## 1. 本次执行范围与账号

首轮采用一名指定测试人员 A：A 在 Backend 中是组织管理员，在腾讯会议中有企业管理员角色、相应 API/录制权限；创建测试还需要 A 的账号具备对应会议创建能力。采用 A 本人的 Backend 登录令牌。另准备无目标内容授权的员工 B，验证拒绝访问。

这只是首轮部署验证用的测试账号配置，不是把日常所有员工都设为管理员。测试只使用已批准的非敏感会议。Backend 账号和腾讯账号必须由管理员确认对应关系，不按姓名猜测。

先执行授权与只读测试，再单独启用创建、媒体下载和 MCP。API 调用是验收入口，不要求先发布新的会议 Portal。

## 2. 凭证对照：不要只填一个 appid + appsecret

| 腾讯配置页面中的值 | 网关登记字段 | 用途 |
|---|---|---|
| 自建应用企业 ID（AppId） | `tencent_corp_id` | 企业标识 |
| 自建应用应用 ID（SdkId） | `sdk_id` | 此腾讯应用标识 |
| 自建应用 SecretId | `secret_id` | 请求签名标识 |
| 自建应用 SecretKey | `secret_key` | 请求签名密钥 |
| OAuth 应用企业 ID | `tencent_corp_id` | OAuth 应用所属企业 |
| OAuth 应用 ID | `sdk_id` | OAuth 客户端应用标识 |
| OAuth 客户密钥 | `oauth_secret` | 即此通道所需的 appsecret，不能当作 AK/SK SecretKey 使用 |
| 事件订阅 Token | `webhook_token` | 回调验签 |
| 事件订阅 EncodingAESKey | `webhook_encoding_key` | 回调解密；43位 Base64 文本，按控制台实际值填写 |
| OAuth 授权返回的 open_corp_id | `allowed_open_corp_ids` | 授权用户企业的允许列表；不默认等于 AppId |

AppId 是企业 ID，SdkId 是应用 ID。AK/SK 必须配置两项标识和一对密钥，不能只有 appid/appsecret。OAuth 应用的客户密钥则对应 `oauth_secret`。[T01][T02][S02]

另外还有三类**不属于腾讯应用凭证**的值：

- Backend 登录 `access_token`：证明员工是谁。
- 网关登记内部应用后返回的 `client_secret`：证明哪个内部系统在调用。
- 网关 `/auth/exchange` 签发的 `access_token`：用于访问 Meeting REST；MCP 另签 `/mcp` 受众。

腾讯应用密钥通过管理接口登记后，由网关加密保存到数据库。不是向 `.env` 添加无源码依据的 `TENCENT_APPID`、`TENCENT_APPSECRET`。

## 3. 在腾讯会议后台先取得应用凭证

### 3.1 企业自建应用

进入企业管理员的“企业管理 → 高级 → 企业自建应用”（以当前后台菜单为准）。新建或选择**企业级**应用，记录企业 ID、应用 ID、SecretId、SecretKey。核对应用可用成员包含 A、A 具备所调用资源的查看权限。[T03]

安全配置中填入指定服务器**实际出站公网 IP**。API 容器与 Worker 容器都要使用该出口。前端访问域名所解析的 IP、宿主机内网 IP、负载均衡入站 IP，都不能直接等同于出站 IP。[T02]

此时先不要保存无法验证的事件 URL。先按第4—7节把网关启动并登记应用，取得真实 `receiver_id` 对应 URL，再回到腾讯后台保存事件订阅。

### 3.2 OAuth 第三方应用

保留现有 OAuth 应用，记录企业 ID、应用 ID、客户密钥。配置：

| 配置 | 填写 |
|---|---|
| 授权回调域名 | 网关的 HTTPS 域名；完整回调路径在应用登记后从 setup 接口取得 |
| IP 白名单 | 网关 API / Worker 实际出站公网 IP |
| 权限范围 | 本次使用的用户会议查询、录制/转写/纪要和创建权限；以腾讯后台可申请、已批准的权限为准 |
| 测试成员 | 当前应用仍在测试阶段时，按腾讯后台要求加入 A |
| H5 可信域名、会中扩展地址 | 本轮接口联调不依赖会中 H5，不作为启动前置条件 |

OAuth 回调域名、事件 Webhook URL、H5 可信域名不是同一项配置。[T02]

## 5. 生成网关配置，接通现有 Backend

### 5.1 生成 .env

首次生成，在网关仓库根目录执行：

```bash
python3 -m app.cli generate-env \
  --public-base-url "$MEETING_BASE_URL" \
  --portal-base-url "$PORTAL_BASE_URL" \
  --backend-url http://host.docker.internal:4510 \
  --database-host postgres
chmod 600 .env
```

`http://host.docker.internal:4510` 只适用于 Backend 在同一宿主机且该端口可达的情况。Backend 位于其他服务器时，替换为 API 与 Worker 都能访问的真实内网地址；不要把容器中的 `127.0.0.1` 当成 Backend 宿主机。[S03]

生成器拒绝覆盖已有 `.env`。已有部署应保留 `DATABASE_URL`、`KEYRING_JSON` 和数据库卷，修改所需配置，不重新生成密钥覆盖既有数据。[S03]

首轮保持：

```dotenv
ENVIRONMENT=production
MEETING_ENABLED=true
MEETING_CREATE_ENABLED=false
MEETING_CORP_SYNC_ENABLED=false
MEETING_MEDIA_DOWNLOAD_ENABLED=false
MEETING_MCP_ENABLED=false
MEETING_AUTO_RECORD_ENABLED=false
```

`generate-env` 没写出最后一项时，代码默认也是 false。需要修改时编辑 `.env`，不要 `source .env`；它包含 JSON 配置值，不是通用 Shell 文件。

核对以下字段：

| 字段 | 要求 |
|---|---|
| PUBLIC_BASE_URL | 实际网关 HTTPS origin，不带 `/api/v1` |
| PORTAL_BASE_URL | 现有 Portal 的实际 HTTPS origin；当前 OAuth 默认完成页仍使用它 |
| NODESKCLAW_BACKEND_URL | API/Worker 可达的 Backend 服务地址 |
| BACKEND_SERVICE_TOKEN | 与 Backend 的 `MEETING_IDENTITY_SERVICE_TOKEN` 完全相同 |
| ALLOWED_HOSTS | 包含网关域名、localhost、127.0.0.1；不填 `*` |
| CORS_ORIGINS | 使用浏览器时填实际已有内部页面的 origin；脚本调用没有 Origin 头 |
| KEYRING_JSON / ACTIVE_KEY_ID | 保持一致并离线备份，禁止写进联调报告 |
| STORAGE_PATH | 容器内 `/data/private`，API 与 Worker 共用私有卷 |

### 5.2 安装 Backend 身份接口

**在持有现有 Backend 源码的服务器执行**；将同一版网关源码或 integration 模块同步过去，不要求把整套 Backend 搬到白名单服务器。

```bash
python3 /opt/meeting-gateway/scripts/integrate.py --repo /opt/nodeskclaw --dry-run
# 审核变更与备份位置后再执行：
python3 /opt/meeting-gateway/scripts/integrate.py --repo /opt/nodeskclaw --apply
```

安装器同时包含 Portal 增量文件；本轮不依赖 Portal 构建通过。不能因为 UI 暂未发布就跳过 Backend 身份接口。

Backend 进程配置：

```dotenv
MEETING_IDENTITY_SERVICE_TOKEN=与网关BACKEND_SERVICE_TOKEN相同的随机值
```

通过现有密钥管理方式复制，不在终端打印或发送聊天。按现有 Backend 部署流程重启该服务。当前仓库不提供你们 Backend 的服务名和部署文件，不能把网关的 Compose 命令当成 Backend 重启命令。

身份准备改为：操作员输入账号密码，调用网关 `POST /api/v1/auth/account-login` 取得本地 `ms_` 会话，再按需交换业务令牌。不要安装身份桥，不要调用下面三个接口，不要把员工密码写入 `.env`。

```http
GET  /api/v1/auth/meeting-context
POST /api/v1/internal/meeting/principals/resolve
POST /api/v1/internal/meeting/principals/search
```

## 6. 启动 PostgreSQL、迁移、API 与 Worker

在网关仓库根目录：

```bash
cd "$MEETING_REPO"
docker compose --env-file .env -f deploy/compose.yaml config --quiet
docker compose --env-file .env -f deploy/compose.yaml up --build -d postgres migrate api worker
docker compose --env-file .env -f deploy/compose.yaml ps -a
docker compose --env-file .env -f deploy/compose.yaml logs --tail=80 migrate
docker compose --env-file .env -f deploy/compose.yaml exec -T api python -m app.cli check
```

判断：postgres 健康；migrate 退出码为0；api、worker 持续运行；配置 check 返回 `valid=true`。`migrate` 正常退出不是异常。[S05]

```bash
# 在启动日志中仅查分类错误，不直接打包所有含授权信息的日志。
docker compose --env-file .env -f deploy/compose.yaml logs --tail=80 api worker
curl --noproxy '*' -fsS http://127.0.0.1:4522/health/live
curl --noproxy '*' -fsS http://127.0.0.1:4522/health/ready
```

`/health/ready` 要检查 `database:true` 和 `backend:true`，不能只检查 HTTP200；Backend 的成员解析还要通过下一节的真实登录令牌检查。

当前 Dockerfile 仍为 `pip install .`，没有冻结使用 uv.lock。[S06] 本轮可记录实际镜像后联调，但不得把镜像依赖当成与 `uv sync --frozen` 一定一致。保留实际镜像信息：

```bash
mkdir -p "$KIT/evidence"
git rev-parse HEAD > "$KIT/evidence/commit.txt"
docker compose --env-file .env -f deploy/compose.yaml images > "$KIT/evidence/images.txt"
docker compose --env-file .env -f deploy/compose.yaml ps -a > "$KIT/evidence/containers.txt"
docker compose --env-file .env -f deploy/compose.yaml exec -T api python -m pip freeze \
  > "$KIT/evidence/runtime-dependencies.txt"
```

不要执行 `docker compose config` 后直接把完整输出放进报告，它会展开环境中的秘密值。

### 6.1 HTTPS 入站

使用仓库 `deploy/nginx.conf.example` 配置独立 server：替换 `server_name`、证书、允许访问的内部系统/VPN来源网段，反代到 `127.0.0.1:4522`。不要沿用示例 `10.0.0.0/8` 假定现场一定允许访问。[S05]

```bash
# 首次安装；已有同名配置先审核，不覆盖。
sudo cp --no-clobber deploy/nginx.conf.example /etc/nginx/conf.d/meeting-gateway.conf
sudoedit /etc/nginx/conf.d/meeting-gateway.conf
sudo nginx -t
sudo systemctl reload nginx
```

保持 `/callbacks/tencent/` 可被腾讯访问；内部 REST/管理入口仍限制内部系统和 VPN。代理必须保留 Host；回调路径不得要求内部登录。禁止使用 `curl -k` 掩盖证书错误。

### 6.2 检查 API、Worker 的出站 IP

使用企业批准的“返回请求来源 IP、响应为纯文本 IP”的检查地址；没有该地址时，由网络管理员从 NAT/防火墙记录核对，不虚构一个检测结果。

```bash
export IP_ECHO_URL=https://企业批准的出口检查地址
export EXPECTED_EGRESS_IP=腾讯后台已登记的公网IP

for SERVICE in api worker; do
  docker compose --env-file .env -f deploy/compose.yaml exec -T \
    -e IP_ECHO_URL="$IP_ECHO_URL" -e EXPECTED_EGRESS_IP="$EXPECTED_EGRESS_IP" \
    "$SERVICE" python - <<'PY' > "$KIT/evidence/${SERVICE}-egress.txt"
import ipaddress, os, urllib.request
opener=urllib.request.build_opener(urllib.request.ProxyHandler({}))
with opener.open(os.environ['IP_ECHO_URL'],timeout=10) as response:
    actual=str(ipaddress.ip_address(response.read(256).decode().strip()))
expected=str(ipaddress.ip_address(os.environ['EXPECTED_EGRESS_IP']))
print('observed_egress_ip='+actual)
print('matches_allowlist='+str(actual==expected).lower())
raise SystemExit(0 if actual==expected else 1)
PY
  test "$?" -eq 0 || { echo "$SERVICE 出口核对失败"; break; }
done
```

通用出口检查只证明到检查地址的路径。腾讯 API 存在不同路由、代理或 IPv6 出口时，还需按实际腾讯请求/网络日志核对。不得仅设置 `X-Forwarded-For` 伪装来源。

## 7. 调试会话、真实员工身份与初始化

后续操作统一在工具包目录执行。不要把脚本或原始响应放进网关受版本控制的源码目录。

```bash
cd "$KIT"
source ./session.sh
cp -n templates/manual-checks.json manual-checks.json
python3 tools/store.py --out private/backend-a.token
```

按提示粘贴 A 登录已有内部系统后取得的 **Backend access_token**。不是腾讯 access_token，不是网关 client_secret。文件权限为0600，不回显。

```bash
python3 tools/call.py --base "$BACKEND_PUBLIC_BASE_URL" \
  --path /api/v1/auth/meeting-context --auth-file private/backend-a.token \
  --label IDENTITY --out private/backend-context.json \
  --expect-status 200 --equals data.is_active=true --equals data.member_role=admin \
  --notempty data.member_id --notempty data.org_id

export MEMBER_A=$(jq -er '.data.member_id' private/backend-context.json)
export ORG_ID=$(jq -er '.data.org_id' private/backend-context.json)

python3 tools/call.py --path /health/ready --no-auth \
  --label READY --out private/ready.json \
  --equals database=true --equals backend=true

admin --method POST --path /api/v1/admin/bootstrap \
  --label SETUP-BOOTSTRAP --out private/bootstrap.json --equals data.bootstrapped=true
```

bootstrap 只执行一次。遇到409，先检查是否已经初始化、当前员工有没有管理授权，不能把409自动当成功，也不删除数据库重来。

## 9. 完成腾讯事件订阅和 STS 测试

在腾讯自建应用的事件订阅中填入：

- URL：上一节返回的 `webhook_url`。
- Token：`private/tencent-aksk.json` 的 `webhook_token`。
- EncodingAESKey：同文件的 `webhook_encoding_key`。
- 事件：`common.sts-token`、本次需要的录制完成/失败、转写生成、纪要生成事件。事件名称以腾讯控制台实际支持列表为准。

保存时，腾讯会发起 GET 校验。当前代码返回原始解密文本，不是统一 JSON；POST 正文返回 `successfully received callback`。[S09] 无签名的手工 GET 被拒绝不表示回调接口坏了。

```bash
admin --path "/api/v1/admin/applications/$APP_AKSK/setup" \
  --label WEBHOOK --out private/aksk-setup-verified.json --notempty data.webhook_verified_at

printf '%s\n' '{"probe":"history"}' > private/probe-history.json
admin --method POST --path "/api/v1/admin/connections/$CONN_AKSK/diagnostics" \
  --json private/probe-history.json --label AKSK-LIST --out private/aksk-history-diagnostic.json \
  --equals data.status=PASSED

printf '%s\n' '{"valid_hours":6}' > private/sts-request.json
admin --method POST --path "/api/v1/admin/connections/$CONN_AKSK/sts" \
  --json private/sts-request.json --expect-status 202 \
  --label SETUP-STS-REQUEST --out private/sts-request.response.json --notempty data.request_id

printf '%s\n' '{"probe":"configuration"}' > private/probe-configuration.json
admin --method POST --path "/api/v1/admin/connections/$CONN_AKSK/diagnostics" \
  --json private/probe-configuration.json --label STS --out private/sts-configuration.json \
  --equals data.sts_request_status=ACTIVE --equals data.webhook_verified=true
```

若最后一步尚未 ACTIVE，等待5秒后只重复 configuration 检查；不要不断重新生成 STS。生成可能与 Worker 维护过程并发，观察“最新请求状态 + 后续转写调用”而不是泄露实际票据。`valid_hours` 只接受6/12/24；网关向腾讯转换成 `valid_time`。票据通过 `common.sts-token` 回传，生成响应本身不是票据。[T04][T05]

观察回调：

```bash

  --label CHECK-EVENT-INBOX --out private/events-inbox.json
jq '.data.items[] | {event_type,state,processed_at,last_reason}' private/events-inbox.json
```

history 诊断默认只测近期窗口并返回数量。`PASSED + returned_count=0` 可以证明该请求被接受，不能证明目标会议已经找到。

## 15. 内部系统事件接收与生态联调

### 15.1 配置内部事件接收地址

地址必须是内部系统实际拥有的 HTTPS URL。下面的本地接收器仅用于接口联调，绑定127.0.0.1，由已有 Nginx 暴露；不新增登录系统。

内部系统机器上的 Nginx location 示例（放入已配置真实证书的 server 中）：

```nginx
location = /meeting-events {
    # 根据网关实际来源添加网络限制；保留HMAC校验。
    access_log off;
    proxy_pass http://127.0.0.1:9099;
    proxy_set_header Host $host;
    proxy_connect_timeout 3s;
    proxy_read_timeout 8s;
    client_max_body_size 1m;
}
```

网关 `.env` 中允许此**确切域名**：

```dotenv
NOTIFICATION_ALLOWED_HOSTS=["填写内部事件接收域名"]
NOTIFICATION_ALLOWED_NETWORKS=[]
```

接收地址 DNS 解析为私网 IP 时，额外填写网关被批准访问的精确 CIDR，例如单个地址的 `/32`；不是开放所有私网。网关 `SafeHTTP` 检查域名和实际解析地址，不能只添加域名后假设私网一定可达。

重建 API、Worker 使配置生效。订阅应在样本内容首次生成/读取前登记。

### 15.2 登记订阅

```bash

python3 - <<'PY'

PY

```

把签名密钥通过既有秘密管理通道放到内部接收服务器，不通过公共聊天、报告、命令参数传递。内部接收服务器运行：

```bash
python3 tools/event_receiver.py --secret-file private/event-signing.secret \
  --db private/events.sqlite3 --evidence evidence/events --port 9099
```

保持进程运行，再触发12节内容获取或14节创建。当前**实际内部事件名**是 `meeting.asset.ready`、`meeting.create.succeeded` 等，不能沿用之前方案中的拟定 `transcript.ready`、`minutes.ready` 直接订阅。[S16]

签名合同：[S16]

```text
X-Meeting-Event-ID
X-Meeting-Timestamp
X-Meeting-Nonce
X-Meeting-Signature: sha256=<HMAC-SHA256十六进制>

签名原文 = timestamp UTF-8 + "." + nonce UTF-8 + "." + HTTP原始body字节
签名密钥 = 本订阅返回的 signing_secret
```

接收器校验签名、5分钟时间偏差和 header/body event_id 一致性，再持久化 event_id 与内容摘要；重复相同事件返回200。接收器不会把正文发给第三方服务。5分钟窗口是本操作包接收器策略，不是腾讯 Webhook 协议要求。

验收 EVENT 的全部条件：腾讯样本产生了真实事件；网关收件箱正确处理；对应内容能通过内部 API 读取；内部系统收到正确 resource_id 的签名通知。接收一个人为构造的签名事件，只能证明接收器能验签，不能代替腾讯端到端证据。

已缓存资产没有变化时可能不再发送 ready。选择新样本或新生成版本，不通过修改数据库伪造事件。接收端迟迟没有事件时查看 OUTBOX 作业 last_reason、域名/CIDR允许列表、订阅 client/member 对该资源的权限。

## 18. 生成生态联调报告

### 18.1 证据分区

```text
private/                          不上传：密钥、令牌、原始响应、转写、纪要、媒体

  client.response.json

  *.receipt.json                  HTTP状态、显式断言、trace_id、代码SHA、响应摘要

  sample-match.md
  create-match.md
  events/*.json                   签名校验后的事件ID、资源ID与摘要
manual-checks.json                 执行人及人工核对项
```

不要把 private/、.env、完整回调 auth_code/state、网关 client_secret、腾讯密钥或签名下载地址加入证据包。原始数据的保留和清理由企业批准策略决定。

### 18.2 填写人工核对项

打开 `manual-checks.json`，填写 operator、server、internal_system。每项只在实际核对后改状态；PASSED 必须附上 evidence/ 内相对文件路径。例如下面只是**填写格式**，实际值应来自本次执行：

```json
{
  "status": "PASSED",
  "observation": "API/Worker出口均与腾讯登记IP一致，真实只读请求已通过；镜像ID记录在images.txt。",
  "evidence_files": ["api-egress.txt", "worker-egress.txt", "images.txt", "containers.txt"]
}
```

没有测试的项保留 NOT_RUN。失败写 FAILED；等待或环境不具备写 BLOCKED。脚本只验证证据文件存在和基本关联，不代替操作员判断截图或日志是否证明该现象。

### 18.3 生成报告

```bash
# 只验证“可以继续开展腾讯授权调试”：
python3 tools/report.py --scope authorization --out 腾讯会议授权联调报告.md

# 两条通道完成真实样本转写与纪要读取：
python3 tools/report.py --scope read --out 腾讯会议只读联调报告.md

# 加入真实创建、下载、内部系统签名事件：
python3 tools/report.py --scope ecosystem --out 腾讯会议生态联调报告.md

# 单独MCP基本调用范围：
python3 tools/report.py --scope mcp --out 腾讯会议MCP联调报告.md
```

报告同时生成 `.md.json`，记录来源回执与摘要。缺少必需证据、HTTP202受理未完成、版本不匹配、受版本控制文件有未审查修改、使用HTTP而非HTTPS，均不得判为本范围 PASSED。报告命令非零退出是门禁结果，不用 `|| true` 把它变成通过。

证据包只打包报告和 evidence/：

```bash
tar -czf meeting-evidence.tar.gz evidence manual-checks.json \
  腾讯会议生态联调报告.md 腾讯会议生态联调报告.md.json
sha256sum meeting-evidence.tar.gz > meeting-evidence.tar.gz.sha256
```

### 18.4 报告中要保留的边界

| 项目 | 不应替代成什么 |
|---|---|
| health/ready通过 | 不等于腾讯鉴权通过 |
| 诊断HTTP200 | 不等于 data.status=PASSED |
| history空列表 | 不等于目标样本可读取 |
| STS生成请求202 | 不等于票据ACTIVE，更不等于内容可读取 |
| 源查询job成功 | 不等于本地权限和样本映射都正确 |
| 腾讯OAuth回跳 | 不等于连接已完成员工确认 |
| 创建202 | 不等于腾讯已创建成功 |
| 事件验签成功 | 不等于该事件来自本次真实样本链路 |
| 手写PASSED | 不等于有实际命令、结果和证据 |
| SDK脚本运行 | 不等于智能体委托及所有工具验证完成 |

## 19. 故障定位与停止条件

| 现象 | 先检查 | 本轮处理 |
|---|---|---|
| api/worker不停重启 | .env校验、密钥、数据库URL、私有卷权限、迁移日志 | 先恢复启动，不测试腾讯 |
| ready的backend=false | 容器到Backend地址、DNS、端口、/health | 再执行真实context/resolve，不以200掩盖失败 |
| admin/bootstrap 403 | A不是Backend组织管理员、成员停用或强制改密 | 不关闭鉴权；使用经批准的正确账号 |
| bootstrap/application创建409 | 已有初始化或相同应用 | 查既有记录，不删库重来 |
| 网关本身HTTP400/403 | Host、Origin、Nginx来源限制 | 与腾讯上游错误分开排查 |
| UPSTREAM_CREDENTIAL_INVALID | 腾讯AppId、SdkId、SecretId、SecretKey是否同一应用 | 不混用企业微信或腾讯云其他应用密钥 |
| 腾讯IP相关拒绝 | API/Worker实际NAT公网出口，是否有不同IPv6/代理路由 | 由网络/腾讯后台修正实际允许来源 |
| STS_NOT_READY/等待回调 | 腾讯订阅、事件URL、同一Token/AESKey、Worker运行、INBOX状态 | 不手工向数据库写STS |
| CORP_MISMATCH | open_corp_id没有可信允许记录 | 核实后更新完整应用凭证并重新授权 |
| OAuth回跳后页面404 | 303前回调是否成功、连接是否PENDING_CONFIRMATION | 通过现有API确认，不把后续页面404混作换票失败 |
| /oauth/authorizations因return_to拒绝 | 当前没有oauth_return_uris配置管理入口 | 本轮用11.2现有API，记录产品配置缺口 |
| RETRYING长期不结束 | last_reason、账户权限、配额、票据或内容生成状态 | 到轮询截止时间记BLOCKED，不无限等 |
| 源查询成功但AKSK目录不可见 | 来源purpose与权限context不一致 | 使用已批准的RECORDINGS样本流程；记录代码缺陷，不扩成全员全权 |
| CONTENT_NOT_READY/CONTENT_ABSENT | 腾讯端录制、转写、纪要功能和实际生成状态 | 换有明确结果的授权样本，不生成替代摘要 |
| 下载拒绝 | asset类型、员工授权、MEDIA开关、真实域名、票据过期、原生地址是否存在 | 不用公网裸链接绕过下载权限 |
| 无内部事件 | 订阅是否在生成前建立、资源权限、域名/CIDR、OUTBOX last_reason | 不用伪造腾讯事件证明联调成功 |
| OUTCOME_UNKNOWN | 腾讯侧是否已产生会议 | 停止自动重复创建，人工核对原操作 |

## 22. 本包脚本验证范围

本包在隔离环境执行了标准库单元测试和本地回环HTTP测试，覆盖字段断言、缺失字段、HTTP202状态、重定向拒绝、事件签名/时间窗口、空证据报告门禁。没有连接真实腾讯、现有Backend或指定白名单服务器。

`tools/report.py` 生成的初始报告为 BLOCKED、各项 NOT_RUN；它是待填报告，不是已完成的生态联调结果。仓库自带 `scripts/tencent_live_smoke.py` 在本版本已会请求网关 health/ready 和可选 cache 会议详情，但其成功不能替代本手册的上游授权、STS、完整内容和生态链路验证。
